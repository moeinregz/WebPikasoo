# استراتژی SEO — «باقلوا کریم‌اوغلو» (Prompt 12)

خروجی مستندسازی بخش ۲۵ (۱۴ مورد). این سند مکمل کاری است که در Promptهای
۱ تا ۳ (معماری صفحات، صفحه محصول/دسته‌بندی) از قبل پایه‌گذاری شده بود؛
اینجا فقط بخش‌هایی که واقعاً کم بودند (Sitemap، Robots، صفحات شعبه،
Canonical صفحه‌بندی، Structured Data واقعی نظرات، رویدادهای Analytics
کامل) اضافه/تصحیح شدند.

━━━━━━━━━━━━━━━━━━━━
۱. SEO Architecture
━━━━━━━━━━━━━━━━━━━━

بدون هیچ لایه SEO جداگانه — Next.js App Router خودش معماری SEO است:
هر Route یک `generateMetadata`/`metadata` دارد، هر صفحه Server Component
است (HTML کامل در پاسخ اول، نه CSR)، و Structured Data مستقیماً کنار
داده واقعی همان صفحه تولید می‌شود (نه یک سرویس SEO جدا که ممکن است از
واقعیت صفحه عقب بیفتد).

اصل راهنما در کل این مرحله: **هیچ‌چیز در Meta/Schema نباید چیزی را ادعا
کند که در HTML واقعی صفحه نیست.** به همین دلیل مثلاً AggregateRating تا
وقتی نظر واقعی تأییدشده‌ای وجود نداشت، اصلاً در خروجی ظاهر نمی‌شد.

━━━━━━━━━━━━━━━━━━━━
۲. URL Strategy
━━━━━━━━━━━━━━━━━━━━

معماری URL از Prompt ۱ حفظ شده (طبق دستور صریح «اگر معماری قبلی URL
تعریف کرده، همان را حفظ کن»):

```
/                          خانه
/shop                      فروشگاه (همه محصولات)
/shop/[category]           باقلوا، استانبولی، باقلوا عربی، شیرینی خشک، دنر کباب، فست‌فود
/product/[slug]            صفحه محصول
/branches                  فهرست شعب (جدید — Prompt 12)
/branches/[slug]           صفحه هر شعبه (جدید — Prompt 12)
/guide                     Content Hub (جدید — Prompt 12، معماری آماده)
/guide/[slug]              مقاله راهنما (جدید — Prompt 12)
```

بدون پارامتر شناسه در URL (مثل `?id=123`)؛ فقط Slug خوانا. پارامترهای
Query (`page`, `sort`, `unit`, `q`, ...) فقط برای فیلتر/صفحه‌بندی به‌کار
می‌روند، هرگز بخشی از هویت اصلی URL نیستند (به همین دلیل هرگز وارد
Canonical نمی‌شوند — بخش ۱۳).

━━━━━━━━━━━━━━━━━━━━
۳. Metadata Strategy
━━━━━━━━━━━━━━━━━━━━

- **Template مرکزی**: `%s | باقلوا کریم‌اوغلو` در `app/layout.tsx` — هر
  صفحه فقط بخش اول Title را تعیین می‌کند، نه کل رشته.
- **بدون Duplicate Title**: تست خودکار (`lib/seo/__tests__/seo.test.ts`)
  عدم تکرار Title بین محصولات/دسته‌ها را در هر Build بررسی می‌کند.
- **Canonical**: هر صفحه Dynamic (`generateMetadata`) صریحاً `alternates.canonical`
  را با URL نسبی درست تنظیم می‌کند؛ `metadataBase` در Layout مرکزی است.
- **OpenGraph/Twitter**: از همان `metadata.openGraph` استاندارد Next.js
  استفاده شده (Twitter Card به‌صورت پیش‌فرض از OpenGraph استخراج می‌شود
  مگر جدا تعریف شود). تصویر OG هنوز TODO است (نیاز به لوگو/عکس رسمی برند).
- **Robots per-page**: صفحات فیلترشده/جستجوشده (`?q=`, `?sort=`, ...)
  به‌صورت خودکار `noindex, follow` می‌گیرند (بخش ۱۴).

━━━━━━━━━━━━━━━━━━━━
۴. Schema Strategy
━━━━━━━━━━━━━━━━━━━━

| نوع Schema | صفحه | وضعیت |
|---|---|---|
| Organization | همه صفحات (Layout) | ✅ از قبل موجود |
| WebSite + SearchAction | همه صفحات (Layout) | ✅ جدید — Prompt 12 |
| BreadcrumbList | هر صفحه دارای Breadcrumb | ✅ از قبل، اصلاح‌شده (URL مطلق) |
| Product + Offer | صفحه محصول | ✅ از قبل موجود |
| AggregateRating + Review | صفحه محصول | ✅ جدید — فقط وقتی نظر تأییدشده واقعی موجود باشد |
| CollectionPage | صفحه دسته‌بندی | ✅ از قبل موجود |
| LocalBusiness (BakeryOrCafe) | صفحه شعبه | ✅ جدید — فقط فیلدهای واقعی |
| Article | صفحه راهنما | ✅ جدید (آماده، فعلاً بدون محتوا) |

قانون مشترک همه: تولید Schema از همان داده‌ای که در کامپوننت صفحه رندر
می‌شود، نه از یک منبع جدا — تا هرگز Schema و HTML واقعی از هم جدا نیفتند.

━━━━━━━━━━━━━━━━━━━━
۵. Local SEO Strategy
━━━━━━━━━━━━━━━━━━━━

به‌جای Keyword Stuffing (که Prompt صریحاً منع کرده)، Location Intent از
طریق ساختار واقعی صفحات پوشش داده می‌شود:
- `/branches` صفحات را بر اساس شهر (تهران/همدان) گروه‌بندی می‌کند —
  عبارت «شعبه‌های تهران» و «شعبه همدان» طبیعتاً در H2 می‌آید.
- هر `/branches/[slug]` نام شهر را در H1، Meta Title و Meta Description
  به‌طور طبیعی تکرار می‌کند (نه مصنوعی).
- LocalBusiness Schema هر شعبه `addressLocality` واقعی دارد.
- صفحات دسته‌بندی (`/shop/[category]`) به این صفحات شعبه لینک داخلی
  می‌دهند (بخش ۱۶) تا Google رابطه «باقلوا + شهر» را از ساختار لینک‌ها
  استنباط کند، نه از متن تکراری.

━━━━━━━━━━━━━━━━━━━━
۶. Branch SEO Strategy
━━━━━━━━━━━━━━━━━━━━

هر شعبه صفحه اختصاصی دارد (`/branches/[slug]`) با: نام، شهر، تلفن واقعی،
ساعت کاری واقعی، وضعیت کافه، روش‌های ارسال پشتیبانی‌شده، Breadcrumb، و
LocalBusiness Schema. **آدرس دقیق و مختصات جغرافیایی عمداً نمایش داده
نمی‌شوند** — دقیقاً طبق دستور صریح («TODO هستند، نباید حدس زده شوند») —
به‌جایش پیام صریح «به‌زودی تکمیل می‌شود» نشان داده می‌شود؛ در Schema هم
`geo` اصلاً درج نمی‌شود (نه یک مقدار پیش‌فرض جعلی).

━━━━━━━━━━━━━━━━━━━━
۷. Internal Linking Strategy
━━━━━━━━━━━━━━━━━━━━

```
Homepage → CategoryShowcase → هر Category
Category → ProductGrid → هر Product
Category → دسته‌های مرتبط (۴ مورد) + راهنمای مرتبط (Content Hub)
Product → Related Products (بر اساس دسته)
Product → Breadcrumb → Category → Shop → Home
Branch Index → هر Branch
Branch → /shop (مشاهده محصولات)
Guide Article → دسته محصول مرتبط
```

هر پیوند یک رابطه موضوعی واقعی را دنبال می‌کند (نه پیوند تصادفی برای
افزایش تعداد لینک)؛ به همین دلیل Related Articles فقط وقتی رندر می‌شود
که واقعاً مقاله‌ای برای آن دسته وجود داشته باشد.

━━━━━━━━━━━━━━━━━━━━
۸. Sitemap Strategy
━━━━━━━━━━━━━━━━━━━━

`app/sitemap.ts` (Next.js Metadata API — خروجی XML خودکار در `/sitemap.xml`).
پوشش: خانه، فروشگاه، همه دسته‌بندی‌ها، فقط محصولات **فعال** (`isAvailable`)،
همه شعب، و مقالات راهنما (وقتی محتوای واقعی اضافه شود). صفحات خصوصی
(Cart/Checkout/Order/Payment/Admin/Auth) هرگز به این فایل راه پیدا
نمی‌کنند چون Sitemap فقط از کاتالوگ/شعب/محتوا می‌خواند، نه از فهرست کامل
Routeهای پروژه — تست خودکار این را برای هر ۶ پیشوند خصوصی تأیید می‌کند.

━━━━━━━━━━━━━━━━━━━━
۹. Robots Strategy
━━━━━━━━━━━━━━━━━━━━

`app/robots.ts`:
```
User-Agent: *
Allow: /
Disallow: /admin
Disallow: /api
Disallow: /cart
Disallow: /checkout
Disallow: /order
Disallow: /payment
Sitemap: {SITE_URL}/sitemap.xml
```
`/api` هم Disallow است چون پاسخ JSON خام ارزش Index شدن ندارد و فقط
بودجه Crawl را هدر می‌دهد — نه برای «پنهان‌کاری» (این مسیرها همان‌طور هم
پشت Auth/RBAC هستند).

━━━━━━━━━━━━━━━━━━━━
۱۰. Image SEO
━━━━━━━━━━━━━━━━━━━━

**وضعیت صادقانه**: هیچ تصویر واقعی محصول/شعبه/لوگو هنوز دریافت نشده
(TODO مستندشده در `lib/mock-data.ts` از Prompt‌های قبلی). به‌جای تصویر
جعلی یا Placeholder گمراه‌کننده، `ImagePlaceholder` یک بلوک با ابعاد
صحیح (بدون Layout Shift) و `role="img"` + `aria-label` توصیفی نمایش
می‌دهد. `next.config.js` از قبل برای AVIF/WebP پیکربندی شده.

**مسیر آماده برای اتصال تصاویر واقعی** (مستندشده در کد، بدون نیاز به
تصمیم‌گیری بعدی): جایگزینی هر `ImagePlaceholder` با `next/image`، با
`alt` واقعی (نام محصول + Variant)، `width`/`height` صریح، `priority`
فقط برای تصویر اول Above-the-fold، و `loading="lazy"` برای بقیه.

━━━━━━━━━━━━━━━━━━━━
۱۱. Core Web Vitals Strategy
━━━━━━━━━━━━━━━━━━━━

- **LCP**: صفحات محصول/دسته Server-rendered (بدون انتظار CSR)؛ وقتی
  تصاویر واقعی اضافه شوند، اولین تصویر باید `priority` بگیرد.
  `revalidate = 3600` روی صفحه محصول یعنی HTML از Cache سرو می‌شود، نه
  Query دیتابیس در هر درخواست.
- **CLS**: `ImagePlaceholder` ابعاد ثابت (`aspect-square` و مشابه) دارد؛
  هیچ عنصری بدون رزرو فضا اضافه نمی‌شود.
- **INP**: فیلتر/جستجوی فروشگاه سمت کلاینت با تغییر URL (نه Full Reload)
  انجام می‌شود؛ فرم‌های پنل مدیریت State محلی سبک دارند (بدون Redux).
- **TTFB**: صفحات کاتالوگ (Mock Data در حافظه) و صفحات موجودی/سفارش
  (SQLite محلی، بدون Round-trip شبکه به دیتابیس خارجی) هر دو سریع‌اند؛
  گلوگاه احتمالی آینده فقط زمانی است که یک دیتابیس واقعی شبکه‌ای جایگزین
  SQLite شود — آن‌موقع Connection Pooling لازم است (طبق `docs/backend-architecture.md`).

━━━━━━━━━━━━━━━━━━━━
۱۲. Content Strategy
━━━━━━━━━━━━━━━━━━━━

معماری `lib/content/articles.ts` + `/guide` + `/guide/[slug]` کاملاً
آماده و Deploy-پذیر است؛ آرایه مقالات عمداً خالی است (طبق دستور صریح
عدم تولید محتوای جعلی). موضوعات پیشنهادی Prompt (راهنمای خرید، تفاوت
انواع باقلوا، باقلوا استانبولی/عربی چیست، بسته‌بندی، نگهداری، مناسبت‌ها،
معرفی شعب) به‌عنوان راهنمای ساختاری در همان فایل کامنت شده‌اند. افزودن
اولین مقاله واقعی نیازی به تغییر کد ندارد — فقط یک آیتم به آرایه اضافه
می‌شود و در Sitemap/صفحه دسته‌بندی مرتبط خودکار ظاهر می‌شود.

۱۳. Analytics Events
━━━━━━━━━━━━━━━━━━━━

`lib/analytics.ts` — همه ۷ Event خواسته‌شده Prompt، به‌علاوه چند Event
تکمیلی که از قبل وجود داشت:

| Event | محل فراخوانی | وضعیت |
|---|---|---|
| `product_view` | صفحه محصول | از قبل |
| `category_view` | صفحه دسته‌بندی | ✅ جدید |
| `search` | نوار جستجوی فروشگاه | ✅ جدید |
| `add_to_cart` | ProductCard، PurchasePanel | از قبل |
| `begin_checkout` | صفحه Checkout | از قبل |
| `branch_selection` | Checkout (پس از Resolve شعبه) | ✅ جدید |
| `purchase` | تکمیل سفارش | ✅ رفع باگ (قبلاً همیشه `total: 0` بود) |

پیاده‌سازی فعلی `console.debug` است (طبق طراحی قبلی، عمداً — جایگزینی با
GA4/gtag واقعی یک تصمیم DevOps جداست)؛ امضای تابع `track()` طوری طراحی
شده که آن جایگزینی هیچ تغییری در Componentهای صدازننده نیاز ندارد.

یادداشت — Google Search Console (بخش ۲۳ Prompt)
━━━━━━━━━━━━━━━━━━━━

آماده‌سازی فنی لازم قبل از اتصال به GSC:
1. **Verification**: نیاز به دامنه نهایی واقعی (`SITE_URL` در
   `lib/seo/siteConfig.ts` هنوز placeholder است) — یا از طریق DNS TXT یا
   یک فایل/متا‌تگ Verification که بعد از تعیین دامنه اضافه می‌شود.
2. **Sitemap Submission**: `{SITE_URL}/sitemap.xml` از قبل آماده تسلیم است.
3. **Indexing Monitoring / Coverage**: نیازمند Deploy واقعی؛ کد فعلی
   هیچ مانعی برای Crawl صحیح ایجاد نمی‌کند.
4. **Performance / Core Web Vitals در GSC**: داده واقعی فقط بعد از
   ترافیک واقعی روی دامنه نهایی جمع می‌شود.

این مرحله عمداً «فقط آماده‌سازی» است — چون Verification/Submission واقعی
به یک دامنه Live و حساب Google Search Console نیاز دارد که خارج از
محدوده این کد است.
