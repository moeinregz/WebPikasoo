# قرارداد Migration (اضافه‌شده در Prompt 15)

تا قبل از این مرحله، `lib/db/schema.sql` تنها راه ساخت دیتابیس بود
(`CREATE TABLE IF NOT EXISTS` — فقط برای اولین راه‌اندازی امن است). از این
پس، **هر تغییر روی یک دیتابیس Production که از قبل داده واقعی دارد** باید
از این پوشه عبور کند، نه با ویرایش مستقیم `schema.sql`.

## قانون

1. `schema.sql` فقط برای «دیتابیس کاملاً خالی» (اولین راه‌اندازی/تست) دست
   نخورده می‌ماند — می‌توانید ستون/جدول تازه را همان‌جا هم اضافه کنید (برای
   نصب‌های تازه)، **اما** برای دیتابیس‌های موجود، همان تغییر را این‌جا هم به
   شکل یک فایل عددی جدید بنویسید.
2. نام فایل: `NNNN_توضیح-کوتاه.sql` — عدد ۴ رقمی، صعودی، هرگز عوض نشود
   (مثلاً `0001_add_order_priority_column.sql`).
3. هر فایل باید **Idempotent و امن برای اجرای دوباره نباشد لزوماً** (چون
   `scripts/migrate.mjs` هر فایل را فقط یک‌بار اجرا و در جدول
   `schema_migrations` ثبت می‌کند)، اما باید فقط شامل تغییرات ایمن و برگشت‌پذیر
   باشد — تغییرات مخرب (مثل `DROP COLUMN` روی داده واقعی) باید طبق
   `docs/database-migration-guide.md` (بخش «Migration خطرناک») جداگانه
   برنامه‌ریزی شوند، نه این‌جا بی‌فکر نوشته شوند.
4. قبل از اجرای هر Migration روی Production، طبق الزام صریح Prompt، یک
   Backup کامل باید گرفته شده باشد (`scripts/backup-db.sh`).

## اجرا

```bash
node --experimental-strip-types scripts/migrate.mjs
```

(روی Node ≥ 22.13 نیازی به `--experimental-sqlite` نیست — رجوع به
Dockerfile برای نسخه دقیق Pin‌شده.)

اسکریپت هر فایل این پوشه را به ترتیب عددی بررسی می‌کند؛ هر فایلی که در
`schema_migrations` ثبت نشده را داخل یک Transaction اجرا و سپس ثبت می‌کند.
اگر یک فایل شکست بخورد، Transaction آن فایل Rollback می‌شود و اسکریپت با
خطا متوقف می‌شود (فایل‌های بعدی اجرا نمی‌شوند).

فعلاً هیچ فایل Migration واقعی اینجا نیست — کل Schema فعلی هنوز فقط در
`schema.sql` (نسخه پایه) تعریف شده.
